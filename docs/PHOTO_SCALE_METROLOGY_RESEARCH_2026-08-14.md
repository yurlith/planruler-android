# Определение масштаба и размеров по фотографии

Дата: 2026-08-14. Целевой продукт: PlanRuler Mobile, Android, offline-first.

## Итог исследования

Измерения по фотографии реализуемы, но обычная одиночная фотография сама по
себе не содержит абсолютного масштаба. Одинаковое изображение может показывать
реальный объект или его уменьшенную модель. EXIF-фокусное расстояние также не
решает задачу без расстояния до объекта или известной геометрии.

Для строительного применения нужны три отдельных режима:

1. **Фото + плоскость + известный размер** — основной режим для уже снятых
   фотографий. Пользователь задаёт плоскость стены, пола или фасада и реальную
   ширину/высоту либо известный прямоугольный объект. Перспектива компенсируется
   гомографией.
2. **PlanRuler-маркер** — быстрый и наиболее воспроизводимый вариант. В кадре
   находится распечатанный маркер проверенного размера; углы и масштаб могут
   определяться автоматически.
3. **AR-съёмка** — телефон перемещается несколько секунд, а ARCore сохраняет
   положение камеры, плоскости и при наличии Depth API карту глубины. Этот режим
   позволяет измерять разные плоскости и объекты, но работает только во время
   специальной съёмки, а не для произвольного старого JPEG.

Нейросетевую оценку метрической глубины из одного изображения нельзя использовать
как основной источник строительных размеров: результат правдоподобен визуально,
но не имеет достаточной гарантии масштаба. ML допустим только для подсказки границ
стены/пола, после чего масштаб подтверждает пользователь.

## Что уже есть в PlanRuler

Текущая мобильная версия:

- импортирует JPEG/PNG и правильно применяет восемь EXIF-ориентаций;
- хранит изображение в пиксельной системе координат;
- позволяет задать один известный отрезок и выполнить независимую проверку;
- показывает предупреждение для короткой или непроверенной калибровки;
- поддерживает длины, полилинии, площади, углы и аннотации.

Текущее ограничение принципиально: `Calibration` хранит один скаляр
`metersPerDocumentUnit` для всей фотографии. На перспективном снимке масштаб
меняется по изображению, поэтому один скаляр корректен только для почти
фронтальной съёмки и объектов на одной глубине рядом с эталоном.

## Глубокий анализ метаданных съёмки

Предположение «если в фото есть метаданные, можно восстановить результат съёмки»
верно только после классификации метаданных. Одни поля описывают файл, другие —
камеру, третьи действительно содержат метрическую геометрию сцены.

### Уровень 0 — оформление изображения

Поля `PixelXDimension`, `PixelYDimension`, `Orientation`, crop и thumbnail
позволяют правильно совместить пиксели. Они не содержат масштаба. EXIF
`Orientation` — это поворот/отражение изображения, а не пространственная поза
телефона.

### Уровень 1 — оптика и лучи камеры

Полезные стандартные поля:

- `FocalLength` и `FocalLengthIn35mmFilm`;
- `FocalPlaneXResolution/YResolution` и единица focal plane;
- фактический размер изображения;
- Camera2 `LENS_INTRINSIC_CALIBRATION = [fx, fy, cx, cy, skew]`;
- `LENS_DISTORTION`, crop region, zoom ratio и ID физической камеры.

Из них строится матрица камеры:

```text
K = [ fx  s  cx ]
    [  0 fy  cy ]
    [  0  0   1 ]

ray(u,v) = normalize(K⁻¹ · [u,v,1]ᵀ)
```

Это позволяет исправить дисторсию и получить направление 3D-луча для каждого
пикселя, но не сообщает, в какой точке луч встретил объект. Поэтому intrinsics
улучшают геометрию, однако сами по себе абсолютного масштаба не дают.

Для импортированного JPEG нужно учитывать, что ISP телефона мог выполнить
цифровой zoom, crop, стабилизацию и коррекцию объектива. Значения из полного
сенсора нельзя напрямую применять к готовому JPEG без преобразования в систему
координат сохранённого crop.

### Уровень 2 — расстояние фокусировки

EXIF допускает `SubjectDistance` в метрах, а Camera2 — `LENS_FOCUS_DISTANCE`.
Если известны `Z` и `fx`, для фронтальной плоскости можно получить приближение:

```text
metersPerPixel ≈ Z / fx
length ≈ pixelLength · Z / fx
```

Но это расстояние до плоскости фокусировки/главного объекта, а не depth каждого
пикселя. Оно может отсутствовать, быть `unknown/infinity`, иметь грубую
квантизацию или быть объявлено камерой как `UNCALIBRATED`. Телефон также может
фокусироваться на трубе перед стеной. Поэтому этот путь допустим только как
`DISTANCE_HINT / LOW_CONFIDENCE`, с обязательным подтверждением одного размера.

### Уровень 3 — стандартный depth внутри фотографии

Это уже настоящая основа для метрических измерений:

- Android `DEPTH_JPEG` (API 29+) — JPEG с XMP Dynamic Depth;
- Google GDepth — depth image в XMP с `Near`, `Far`, `Units`, форматом
  `RangeLinear`/`RangeInverse` и optional confidence;
- Android Dynamic Depth 1.0 — профили `DepthPhoto` и `ARPhoto`;
- Apple auxiliary depth/disparity в JPEG, HEIF и DNG;
- Android `DEPTH16` — диапазон в миллиметрах плюс confidence;
- `DEPTH_POINT_CLOUD` — XYZ-точки и confidence; при camera depth capability
  координаты задаются в метрах.

Dynamic Depth особенно ценен. Профиль `DepthPhoto` требует согласованные цветное
изображение и depth map. Профиль `ARPhoto` способен хранить:

- позу устройства/камеры;
- camera intrinsics (`ImagingModel`);
- горизонтальные и вертикальные плоскости;
- depth maps и изображения;
- world/realm coordinate system;
- confidence и application-specific данные.

Такой файл можно считать контейнером результатов съёмки, а не просто картинкой.
Но PlanRuler обязан проверять `Units`: стандарт прямо допускает depth/point cloud
без метрических единиц, и тогда измерение остаётся определённым лишь с точностью
до общего масштаба.

### Перевод depth в 3D

Если depth хранит осевую координату `z`, точка вычисляется так:

```text
X = (u - cx) · z / fx
Y = (v - cy) · z / fy
Z = z
```

Если формат хранит расстояние вдоль оптического луча, используется
`P = range · ray(u,v)`. Для inverse depth/disparity сначала выполняется
преобразование, заданное метаданными; у Apple disparity в поддерживаемых
`AVDepthData` форматах может быть представлена в `1/meters`.

Для измерения нельзя брать один шумный depth-пиксель. Надёжнее:

1. собрать окрестность точки с confidence выше порога;
2. удалить выбросы медианой/RANSAC;
3. для стены/пола аппроксимировать локальную плоскость;
4. пересечь точный camera ray с этой плоскостью;
5. измерить расстояние между полученными 3D-точками;
6. распространить uncertainty глубины и выбора пикселя на итоговую длину.

Плоскостная аппроксимация даст на стройке более стабильный результат, чем
непосредственная разность двух значений низкоразрешённой depth map.

### Уровень 4 — Motion Photo и многокадровость

Motion Photo содержит высококачественный still и добавленный MP4. Несколько
ракурсов дают параллакс, поэтому можно восстановить camera motion и относительную
3D-геометрию через feature tracking/SfM. Однако стандартный Motion Photo XMP
описывает прежде всего расположение и время видео, а не метрическую траекторию.
Видео без IMU, стереобазы, depth или известного размера всё равно имеет
неопределённый общий масштаб.

Практический pipeline:

- извлечь кадры вокруг presentation timestamp;
- найти и сопоставить устойчивые признаки;
- оценить intrinsics из EXIF/Camera2 или совместно оптимизировать их;
- построить относительные camera poses и sparse point cloud;
- привязать масштаб по depth, известной длине, стереобазе или PlanRuler-маркеру;
- использовать still высокого разрешения для точной установки конечных точек.

Motion Photo — сильный усилитель геометрии, но не самостоятельный источник
метрического масштаба.

### Уровень 5 — стереокамеры телефона

Android logical multi-camera может предоставить два синхронных физических
YUV/RAW-потока. Для них Camera2 требует/предоставляет intrinsics, distortion,
pose rotation и `LENS_POSE_TRANSLATION` в метрах; это физическая стереобаза.
После rectification и stereo matching:

```text
Z = fx · baselineMeters / disparityPixels
```

Это позволяет получить метрическую глубину без печатного маркера. Ограничения:

- не каждый OEM открывает пригодную пару стороннему приложению;
- камеры могут иметь разную экспозицию, фокус и поле зрения;
- sensor sync бывает `CALIBRATED` или только `APPROXIMATE`;
- обычный JPEG системной камеры обычно не содержит два исходных потока.

Поэтому стерео имеет смысл как capability-based режим собственной камеры
PlanRuler, а не как обещание для любого фото из галереи.

### Уровень 6 — ARCore dataset

ARCore Recording & Playback сохраняет MP4 с video, IMU и дополнительными
событиями/метаданными. Можно добавить custom track PlanRuler с pose, intrinsics,
выбранными плоскостями, depth samples и quality на каждый ключевой кадр.

Полагаться только на повторный playback нельзя: документация предупреждает, что
trackables и poses при повторной обработке могут отличаться. Поэтому принятые
во время съёмки метрические результаты нужно сохранять в собственный
versioned `PlanRuler Capture Package`, а MP4 оставлять доказательным и
пересчитываемым исходником.

## Metadata Capability Scanner

Первым техническим компонентом должен стать не «AI scale», а инспектор
возможностей файла. Он ничего не угадывает, а строит паспорт доказательств.

```text
CaptureEvidence
 ├─ sourceSha256, container, mime, dimensions
 ├─ EXIF/XMP namespaces and raw provenance
 ├─ orientation/crop/active camera ID
 ├─ intrinsics + distortion + calibration quality
 ├─ subject/focus distance hint
 ├─ metric depth + confidence + depth definition
 ├─ camera/device/world pose
 ├─ horizontal/vertical planes
 ├─ stereo baseline / physical camera pair
 ├─ motion-photo or AR dataset tracks
 └─ capabilities + warnings + trust level
```

Capability flags:

```text
PIXEL_GEOMETRY
CAMERA_INTRINSICS
LENS_CORRECTION
DISTANCE_HINT
METRIC_DEPTH
DEPTH_CONFIDENCE
CAMERA_POSE
WORLD_PLANES
MULTIFRAME
STEREO_BASELINE
METRIC_RECONSTRUCTION_READY
```

Выбор алгоритма выполняется по доказательствам:

1. `METRIC_DEPTH + INTRINSICS` → прямое 3D с plane fitting;
2. `ARPhoto + WORLD_PLANES` → восстановление сохранённой съёмки;
3. `STEREO_BASELINE + paired frames` → stereo depth;
4. `MULTIFRAME + metric anchor` → metric SfM;
5. `INTRINSICS + DISTANCE_HINT` → только приблизительная локальная шкала;
6. ничего из перечисленного → ручная перспективная плоскость/маркер.

## Доверие и сохранность доказательств

Метаданные нельзя считать автоматически истинными. Они могут быть удалены,
отредактированы, оставлены от исходного файла после crop или не соответствовать
добавленному depth payload. Поэтому:

- исходный файл сохраняется без перекодирования и получает SHA-256;
- отдельно хранится raw EXIF/XMP и нормализованный паспорт;
- проверяются MIME, размеры, ориентация, aspect ratio и соответствие color/depth;
- extended XMP и base64 payload читаются потоково с лимитами размера;
- неизвестные vendor extensions сохраняются, но не влияют на расчёт;
- после редактирования фото depth/pose помечаются `STALE`, пока согласование не
  подтверждено;
- `captured by PlanRuler` и импортированный файл имеют разные уровни provenance;
- GPS, серийные номера и device fingerprint не попадают в обычный экспорт без
  отдельного согласия пользователя.

## Новый продуктовый формат: PlanRuler Survey Photo

Чтобы не зависеть от того, что OEM решил записать в JPEG, собственная камера
PlanRuler должна создавать переносимый локальный пакет:

```text
capture.planruler-photo/
 ├─ manifest.json
 ├─ original.heic|jpg
 ├─ depth.bin|png
 ├─ confidence.bin|png
 ├─ intrinsics.json
 ├─ poses.jsonl
 ├─ planes.json
 ├─ measurements.json
 ├─ preview.jpg
 └─ checksums.sha256
```

Физически это может быть один ZIP-подобный versioned контейнер. Он включается в
зашифрованный локальный backup, не требует сервера и сохраняет всё необходимое
для повторного расчёта после обновления алгоритма.

## Рекомендуемый режим «Измерить готовое фото»

### Сценарий

1. Пользователь импортирует фотографию.
2. Выбирает `Стена`, `Пол`, `Потолок`, `Фасад` или `Своя плоскость`.
3. Ставит четыре точки по углам прямоугольной области. Приложение показывает
   перспективную сетку и позволяет точно увеличить каждый угол.
4. Задаёт эталон:
   - ширина и высота плоскости;
   - размеры известного прямоугольника;
   - готовый PlanRuler-маркер;
   - два независимых лазерных/ручных размера.
5. Приложение строит преобразование из координат фото в метрические координаты
   плоскости.
6. Все точки измерения преобразуются в эту систему до вычисления длины и площади.
7. Пользователь проверяет отдельный контрольный отрезок. Экран показывает не
   абстрактное «точно», а ошибку проверки и область действия калибровки.

Измерения за пределами выбранной плоскости или пересекающие две плоскости должны
блокироваться либо требовать назначения другой плоскости.

### Математическая модель

Четыре точки изображения `(xi, yi)` сопоставляются четырём метрическим точкам
`(0,0)`, `(W,0)`, `(W,H)`, `(0,H)`. Решается гомография `H`:

```text
s · [X, Y, 1]ᵀ = H · [x, y, 1]ᵀ
```

После деления на третью координату каждая экранная точка получает положение в
метрах на плоскости. Длины, периметры и площади вычисляются уже в метрическом
пространстве. Отдельная матрица нужна для каждой стены, пола или другой плоскости.

Для первого выпуска OpenCV не обязателен: решение нормализованной системы 8×8,
обратное преобразование и отрисовку сетки можно реализовать чистым Kotlin.
OpenCV/маркерный детектор понадобится позже для автоматического поиска углов,
линзовой коррекции и ArUco/AprilTag.

## Эталоны масштаба

По убыванию доверия:

1. два независимых размера лазером на выбранной плоскости;
2. жёсткий PlanRuler-маркер с проверочной линейкой;
3. лист A4 или другой подтверждённый прямоугольник, лежащий в той же плоскости;
4. один вручную измеренный длинный отрезок плюс подтверждённая геометрия
   плоскости;
5. дверь, окно, кирпич или плитка только с введённым фактическим размером;
6. «типовой размер двери/кирпича» — лишь предположение с низким доверием.

Распечатанный маркер должен содержать контрольную линию, например 180 mm. Принтер
может изменить масштаб, поэтому пользователь обязан один раз измерить линию и
сохранить фактический размер маркера.

## Режим «Снять и измерить»

Для новой съёмки рекомендуется отдельный CameraX/ARCore workflow:

1. приложение просит медленно сместить телефон влево/вправо;
2. показывает качество tracking, глубины и найденных плоскостей;
3. сохраняет RGB-кадр, camera intrinsics, pose, выбранные 3D-точки и confidence;
4. пользователь отмечает точки во время съёмки или позже на сохранённом кадре;
5. при отсутствии Depth API остаётся ARCore plane/hit-test или ручная
   перспективная калибровка.

ARCore получает глубину преимущественно из движения и может объединять её с ToF.
Наиболее точный рабочий диапазон в обзорной документации Google — примерно
0.5–5 m; в API raw depth ошибка растёт с расстоянием, а гладкие белые стены без
текстуры ухудшают tracking. Поэтому режим обязан подсказывать движение и уметь
отказаться от результата низкого качества.

ARCore должен быть optional: приложение сохраняет работу на устройствах без
Depth API и не требует серверного аккаунта. Основные AR/depth вычисления могут
работать без разрешения `INTERNET` у PlanRuler.

## Модель доверия

Вместо одного статуса `calibrated` сохраняются:

- тип источника масштаба;
- идентификатор плоскости;
- четыре исходные точки и матрицы прямого/обратного преобразования;
- физические размеры и их заявленная погрешность;
- длина эталона в пикселях и доля кадра;
- ошибка обратной проекции углов;
- независимый контрольный отрезок и относительное расхождение;
- EXIF/camera intrinsics и сведения о линзовой коррекции, если доступны;
- AR depth confidence и диапазон расстояний, если использовался AR;
- статус `VERIFIED`, `ESTIMATED`, `LOW_CONFIDENCE` или `REJECTED`.

Рекомендуемые UI-правила:

- зелёный — независимая проверка пройдена и измерение находится внутри плоскости;
- оранжевый — масштаб задан, но независимой проверки нет;
- красный — короткий эталон, вырожденный четырёхугольник, точка вне плоскости,
  плохая глубина или большое контрольное расхождение;
- всегда показывать фактическое расхождение проверки, например `2.4%`, а не
  обещание абсолютной точности;
- не позволять экспортировать низкодоверительный размер без заметной маркировки.

Пороговые значения выпуска нужно получить из полевого датасета, а не назначать
по ощущениям. Начальная цель валидации для плоской ручной калибровки: median
ошибка не более 1% и P95 не более 2% в контролируемых условиях. Это критерий
приёмки будущей реализации, а не текущая характеристика приложения.

## Изменения архитектуры

Нужен новый доменный слой, например `core:photo-metrology`:

```text
PhotoPlane
 ├─ id, pageIndex, polygon
 ├─ realWidthMeters, realHeightMeters
 ├─ imageToPlane[3×3], planeToImage[3×3]
 ├─ reference/provenance
 ├─ verification and uncertainty
 └─ confidence/status

Measurement
 └─ photoPlaneId: String?
```

Обычная PDF-калибровка продолжает использовать скаляр. Фотоизмерение получает
`PhotoPlane`; его нельзя автоматически подменять глобальным скаляром. Экспорт
JSON/PDF/CSV должен указывать режим, плоскость, контрольную ошибку и статус.

## Этапы внедрения

### P-1 — паспорт метаданных

- потоковый EXIF/XMP/container inspector без изменения исходника;
- поддержка JPEG/PNG/HEIC/AVIF/DNG на уровне capability scan;
- обнаружение GDepth, Dynamic Depth, auxiliary depth и Motion Photo;
- нормализация intrinsics, crop, orientation, depth units/definition/confidence;
- экран `Что содержит эта фотография?` с понятными возможностями и рисками;
- `CaptureEvidence`, SHA-256, ограничения payload и fuzz-тесты парсера;
- сохранение результатов инспекции в проект, но без автоматического утверждения
  масштаба.

### P0 — безопасная основа

- чистый Kotlin homography solver и проверки вырожденной геометрии;
- модель нескольких плоскостей и миграция проекта;
- ручные четыре угла + ширина/высота;
- перспективная сетка, zoom-уточнение углов;
- длина, полилиния и площадь внутри плоскости;
- независимая проверка, confidence и audit trail;
- локализация PL/EN/DE/FR/IT/RU;
- экспорт с явным статусом.

### P1 — быстрые эталоны

- пресеты A4 и пользовательских прямоугольников;
- генерируемый PlanRuler-маркер и автоматическое распознавание;
- подсказка границ плоскости с ручным подтверждением;
- коррекция линз для собственной камеры;
- подготовленный адаптер Bluetooth-лазера без привязки к одному производителю.

### P2 — AR-съёмка

- optional ARCore session и проверка поддержки Depth API;
- guided motion, plane/depth hit tests и quality overlay;
- сохранение metric 3D points, camera pose/intrinsics и фото;
- измерения между точками одной или разных плоскостей;
- fallback на P0 для неподдерживаемых устройств.

### P3 — многокадровая реконструкция

- короткий офлайн-проход по комнате;
- объединение кадров/точек и упрощённый план;
- обязательная проверка масштабом или depth/visual-inertial tracking;
- экспорт DXF/SVG после отдельной полевой валидации.

## Набор тестов

- fixtures для обычного EXIF, GDepth, Dynamic Depth `DepthPhoto`/`ARPhoto`,
  `DEPTH_JPEG`, Motion Photo и HEIF auxiliary depth;
- повреждённый/обрезанный extended XMP, неверный base64, огромный payload,
  несогласованные размеры color/depth и защита от исчерпания памяти;
- преобразование `RangeLinear`, `RangeInverse`, axial depth, ray range и
  disparity в метрические XYZ;
- crop/orientation/intrinsics mapping и обнаружение устаревшей depth map после
  редактирования изображения;
- plane fitting с выбросами, confidence threshold и распространение
  uncertainty на длину;
- identity/affine/projective homography и обратный round-trip;
- известные длины и площади на синтетической перспективной сетке;
- перестановка углов, самопересечение, почти коллинеарные и слишком малые
  четырёхугольники;
- property-based тесты случайных невырожденных преобразований;
- все восемь EXIF-ориентаций до и после перспективного преобразования;
- синтетические изображения с шумом, blur, тенями и линзовой дисторсией;
- запрет измерения вне плоскости и между несовместимыми плоскостями;
- JSON migration/round-trip и сохранение audit/confidence;
- Compose journey: фото → плоскость → эталон → сетка → проверка → экспорт;
- ARCore supported/unsupported/depth unavailable fallback;
- полевой датасет со стенами, полом, фасадом и трубными узлами, измеренными
  поверенным лазером; отчёт median/P95/max по расстоянию и углу съёмки.

## Конкурентный вывод

- ImageMeter уже показывает правильный базовый паттерн: Perspective Reference
  использует известный прямоугольник и ограничивает измерения его плоскостью.
- Leica DISTO Plan и Bosch MeasureOn делают акцент на назначении реальных
  лазерных размеров линиям на фото, а не на угадывании масштаба.
- Polycam измеряет 3D captures, то есть использует полноценный capture workflow,
  а не произвольный одиночный JPEG.
- magicplan на Android предлагает AR Room Scan, что подтверждает ценность
  отдельного режима съёмки, но не отменяет ручной fallback.

Отличие PlanRuler должно быть не в обещании «AI узнает всё по одной фотографии»,
а в объединении плоской фотограмметрии, проверяемого эталона, видимой погрешности,
офлайн-хранения и последующего монтажного расчёта в одном проекте.

## Реализовано в `1.4.x`

Первый исполняемый этап исследования встроен именно в PlanRuler Mobile:

- при импорте PNG/JPEG вычисляются SHA-256 исходника и размер файла;
- из EXIF нормализуются make/model/lens, ориентация, реальное и 35-мм
  фокусное расстояние, digital zoom, SubjectDistance и focal-plane resolution;
- быстрый scanner читает не более 4 MiB начала и 1 MiB конца контейнера и
  распознаёт сигналы GDepth, Dynamic Depth/DEPTH_JPEG, ARPhoto, Motion Photo и
  Apple auxiliary depth;
- readiness разделён на `REFERENCE_REQUIRED`, `APPROXIMATE_FOCUS_PLANE`,
  `METRIC_DEPTH_AVAILABLE` и `AR_SURVEY_AVAILABLE`;
- локальный профиль камеры группируется по make/model/lens/aspect/focal/zoom,
  дедуплицируется по SHA-256 и хранит только обезличенные оптические числа;
- устойчивость объявляется только после минимум трёх разных фотографий и при
  relative MAD не выше 2%; на экране показываются sample count, median и MAD;
- экран «Данные фото» доступен из меню проекта изображения и переведён на RU,
  EN, DE, PL, FR и IT;
- ни SubjectDistance, ни статистический профиль не применяются к калибровке
  автоматически.

### Форматонезависимый decoder в `1.4.1-alpha2-depth-decoder`

Второй исполняемый этап отделяет три уровня: контейнер, кодек payload и
метрическую модель. Расширение файла и MIME от файлового провайдера больше не
являются источником истины.

- JPEG APP1 XMP и extended-XMP собираются по GUID и chunk offset;
- PNG XMP читается из обычного или сжатого `iTXt`;
- неупакованный XMP обнаруживается внутри ISO box container;
- `GDepth:Data` и `GDepth:Confidence` декодируются из base64;
- Dynamic Depth `Container:Directory` разбирается по `DataURI`, `Length` и
  порядку вторичных элементов; начало данных вычисляется от конца файла, поэтому
  основной файл может быть JPEG, PNG или HEIF;
- payload выбирается по сигнатуре байтов. Поддерживаемые Android codec rasters
  читаются через `ImageDecoder`/`BitmapFactory`; grayscale PNG 8/16 bit имеет
  отдельный lossless decoder;
- `RangeLinear` и `RangeInverse` переводятся в `FloatArray` метров с нормализацией
  `m/cm/mm`; confidence приводится к диапазону 0…1 и размеру depth map;
- итоговый `MetricDepthMap` одинаков для любого входного контейнера и содержит
  ширину, высоту, encoding, measure type, source bit depth, min/median/max,
  число валидных samples и выборку по нормализованным координатам;
- декларация depth больше не переводит снимок в `METRIC_DEPTH_AVAILABLE`:
  readiness повышается только после успешного численного декодирования в метры;
- лимиты защищают мобильное устройство: файл 96 MiB, отдельный payload 32 MiB,
  карта 16 миллионов точек.

Нативный Apple auxiliary depth остаётся отдельным адаптером: на Android нет
публичного аналога Apple Image I/O для извлечения auxiliary dictionary из
HEIF/JPEG. Такой файл теперь получает явный статус `UNSUPPORTED_PAYLOAD`, а не
ложное подтверждение метрического масштаба.

### Проверяемый кандидат общей формулы

Для одинакового physical lens/crop/aspect исследуется безразмерная постоянная:

`k = f_px / sqrt(width_px² + height_px²) = f_35 / 43.2666`

Тогда для нового кадра того же профиля:

`f_px = median(k) * sqrt(width_px² + height_px²)`

А локальная гипотеза масштаба на подтверждённой фронтопараллельной плоскости с
расстоянием `z` имеет вид:

`scale(z) = z / f_px` metres per pixel.

Это не доказывает единую метрическую шкалу фотографии: при перспективе `z`
меняется по изображению. Формула становится метрической только с depth map,
известной плоскостью/размером или другим проверяемым якорем. Независимая оценка
через focal-plane resolution используется как cross-check, а не усредняется
молча с 35-мм оценкой.

### Реализованные автоматические тесты этого этапа

- 7 domain-тестов оптики, readiness, depth units и median/MAD;
- 4 parser-теста GDepth, Dynamic Depth/ARPhoto, Motion Photo и неполного depth;
- Android fixtures с реальным EXIF round-trip, SHA-256, локальным профилем и
  порогом устойчивости после трёх дедуплицированных снимков;
- Compose/SAF journey: rotated JPEG → меню проекта → инспектор → предупреждение
  об отсутствии принятого масштаба → дальнейшая ручная калибровка.
