# План: 3D-движок PlanRuler v2 — параметрика, полные три измерения, отдельный API

Дата: 2026-08-16. Ветка: `hardening/release-candidate`.
Статус: **план на утверждение**, код не менялся.

---

## 1. Что найдено

3D-движок в проекте один — модуль `core/fabrication-3d` (чистый Kotlin/JVM, 1333 строки
основного кода + 380 строк тестов). Сторонних 3D-библиотек нет, рендер собственный.

| Файл | Строк | Роль |
|---|---|---|
| `Math3D.kt` | 233 | `Vec3`, `Quaternion`, `Transform3D`, `Frame3D` — двойная точность, мм |
| `Assembly3D.kt` | 244 | Граф деталь/порт/соединение, `validate()`, `attach()` |
| `ParametricParts3D.kt` | 157 | Фабрики: труба, отвод, фланец Type 11, равнопроходный тройник |
| `Mesh3D.kt` | 339 | Тесселяция в треугольники/полилинии/метки, габаритный бокс |
| `ManualChain3D.kt` | 252 | Ручной редактор цепочки, undo/redo |
| `SpatialAssemblySolver3D.kt` | 281 | Решатель маршрута |
| `FlangedOffsetAssembly3D.kt` | 127 | Адаптер 2D-расчёта → 3D-граф |

Рендер: `feature/pipe-calculator/ParametricAssembly3DView.kt` (599 строк) — собственный
программный растеризатор на Compose Canvas: алгоритм художника, перспектива/ортография,
подсветка по нормали, пикинг тапом, координатный триэдр.

Ядро математики сделано корректно и его переписывать не нужно. Проблемы — в трёх других местах.

## 2. Диагноз

### 2.1 Почему параметры нельзя изменить

Это не баг UI, а отсутствие модели редактирования. Конкретно:

1. **Уже поставленную деталь изменить нечем.** В API графа есть только `attach()`
   ([Assembly3D.kt:182](../core/fabrication-3d/src/main/kotlin/com/planruler/fabrication3d/Assembly3D.kt#L182)).
   Нет `updatePart`, `removePart`, `insertBetween`, нет пересборки цепочки ниже по потоку.
   Изменить длину поставленной трубы, угол или крен отвода можно только через `undo` до неё.
2. **Профиль каталога жёстко выведен из 2D-расчёта.** `result.toManualChainProfile3D()`
   ([FlangedOffsetAssembly3D.kt:6](../core/fabrication-3d/src/main/kotlin/com/planruler/fabrication3d/FlangedOffsetAssembly3D.kt#L6))
   вызывается в `remember(result)`. Радиус отвода (1D/1.5D/3D), толщина стенки, зазор под
   сварку, класс фланца — берутся из каталога и переопределить их негде: нет ни слоя
   переопределений в модели, ни UI.
3. **Зашитые константы:**
   - `MAX_SUPPORTED_MANUAL_ELBOWS = 5` — жёсткий потолок ([ManualChain3D.kt:251](../core/fabrication-3d/src/main/kotlin/com/planruler/fabrication3d/ManualChain3D.kt#L251));
   - угол отвода `abs(angleDeg) in 15.0..90.0` ([ManualChain3D.kt:155](../core/fabrication-3d/src/main/kotlin/com/planruler/fabrication3d/ManualChain3D.kt#L155)) — 11.25°, 5°, 180° невозможны;
   - набор углов в интерфейсе прибит: `listOf(30, 45, 60, 90)` ([ParametricAssembly3DWorkspace.kt:205](../feature/pipe-calculator/src/main/kotlin/com/planruler/feature/pipecalculator/ParametricAssembly3DWorkspace.kt#L205) и `:333`);
   - `MIN_MANUAL_PIPE_LENGTH_MM = 10.0`;
   - `radialSegments = 24`, `elbowSegments = 24` — качество меша не настраивается;
   - камера: пресеты yaw/pitch фиксированы, zoom зажат `0.55..4.0`, панорамирования нет вообще (жест pan занят орбитой), центр вращения — всегда центр сцены.
4. **Отвод обязан совпадать по диаметру с трубой** ([ManualChain3D.kt:29](../core/fabrication-3d/src/main/kotlin/com/planruler/fabrication3d/ManualChain3D.kt#L29)) — переходы между DN в цепочке запрещены на уровне контракта.
5. **Стартовая точка монтажа не задаётся.** UI вызывает `ManualChainEditorState3D.create(profile)`
   с дефолтами: начало (0,0,0), направление +X, верх +Z. Смонтировать «от этой точки в этом
   направлении» нельзя.

### 2.2 Почему это не полноценные три измерения

Решатель работает только в вырожденных случаях:

- требует **параллельных** торцевых осей — иначе `NON_PARALLEL_TERMINALS`
  ([SpatialAssemblySolver3D.kt:80](../core/fabrication-3d/src/main/kotlin/com/planruler/fabrication3d/SpatialAssemblySolver3D.kt#L80));
- требует, чтобы цель была впереди старта — иначе `TARGET_BEHIND_START`;
- строит ровно две топологии: прямая труба, либо двухотводный офсет **в одной плоскости**,
  повёрнутой креном в 3D (классический rolling offset). Это 3D-ориентация плоской задачи, а
  не пространственная маршрутизация.

Отсутствует: поворот на 90° с офсетом (3–4 отвода), непараллельные торцы, произвольная
ориентация конечного фланца (клокинг по болтам), обход препятствий, тройники и врезки в
маршруте (геометрия тройника есть, но ни редактор, ни решатель его не ставят), редукции
(`FabricationPartKind.REDUCER` и `CAP` объявлены в enum, но соответствующих типов
`PartGeometry3D` не существует — детали такого вида нельзя создать), контроль
самопересечений и минимальных прямых участков между отводами.

### 2.3 Почему движок не является отдельным API

Проект последовательно применяет ports-and-adapters: `engine-api`/`engine-default`,
`document-api`/`document-android`, `project-api`/`project-local`, `export-api`/`export-android`,
`crm-api`/`crm-local`. 3D-модуль — единственный, кто эту конвенцию нарушает:

- пары `*-api` / `*-impl` нет вообще;
- Compose-функции напрямую дёргают синглтоны реализации: `SpatialAssemblySolver3D.solve(...)`,
  `AssemblyMeshBuilder3D.build(...)`, `ManualChainEditorState3D` — минуя ViewModel и `AppGraph`;
- `core/fabrication-3d` зависит от `core:pipe-calculator` — обратная связь домена, движок
  нельзя переиспользовать и нельзя протестировать без калькулятора;
- в `AppGraph` («единственный composition root») 3D-движка нет;
- `scripts/check_architecture.ps1` про `fabrication3d` не знает, нарушение не ловится;
- решение маршрута и построение меша выполняются синхронно в главном потоке внутри `remember{}`.

### 2.4 Безопасность архитектуры — текущее состояние

Сильные стороны: чистый JVM без Android-типов, без сети (в манифесте нет ни одного
`uses-permission`), контракты через `require`, инвариант `validate()` после каждой правки.

Слабые места, которые надо закрыть **до** расширения функционала:

| Риск | Где | Последствие |
|---|---|---|
| Исключения как способ сообщать об ошибке | `require`/`check` по всему движку | UI ловит `runCatching` и печатает `it.message` пользователю ([ParametricAssembly3DWorkspace.kt:436](../feature/pipe-calculator/src/main/kotlin/com/planruler/feature/pipecalculator/ParametricAssembly3DWorkspace.kt#L436)) — утечка внутренних текстов, нелокализуемо, хрупко |
| Нет квот на размер сцены | `AssemblyMeshBuilder3D.build` | Меш = O(деталей × radial × сегментов). Число деталей ничем не ограничено (`maxElbows` ограничивает только отводы) → OOM/ANR |
| Undo-стек не ограничен | `ManualChainEditorState3D` | Неограниченный рост памяти: каждый снимок держит полный граф |
| Нет кодека сборки | `schemaVersion` объявлен, кодека нет | При добавлении сохранения проектов десериализация станет доверенной точкой входа без валидации |
| Вычисления в главном потоке | `remember { AssemblyMeshBuilder3D.build(...) }` | ANR на больших сборках |

## 3. Целевая архитектура

```
core/fabrication3d-api        (чистый Kotlin, без Android, без pipe-calculator)
    типы-значения: Vec3, Quaternion, Transform3D, Frame3D, граф сборки, Mesh DTO
    интерфейсы:    Fabrication3DEngine, RouteSolver3D, AssemblyEditor3D,
                   MeshTessellator3D, AssemblyCodec3D
    результаты:    Fabrication3DResult<T> = Ok | Error(Fabrication3DError)   ← без исключений
    квоты:         EngineLimits3D
        ▲                                   ▲
        │ api                               │ implementation (наружу не течёт)
core/fabrication3d-engine              app/di/AppGraph
    реализация (переезд текущего кода)      val fabrication3d: Fabrication3DEngine
        ▲
        │ адаптер каталога (мост pipe-calculator → профиль, отдельно от движка)
feature/pipe-calculator
    Assembly3DViewModel → только интерфейс, вычисления в Dispatchers.Default
    ParametricAssembly3DView — собственный растеризатор, читает Mesh DTO
```

Два требования заказчика соблюдены буквально: сторонние 3D-движки не подключаются (рендер
и математика остаются своими), а feature-модуль обращается к движку **только** через
интерфейс из `-api`, полученный из `AppGraph`.

## 4. Этапы работ

### Этап 0 — заморозка поведения (защитная сетка)

Золотые тесты на текущие результаты до любого рефакторинга: замыкание маршрута для всех 14 DN,
длины резов эталонной сборки DN50/PN16, число треугольников меша. Рефакторинг не имеет права
их сдвинуть.

### Этап 1 — разделение на API и реализацию

- Создать `core/fabrication3d-api` и `core/fabrication3d-engine`, зарегистрировать в
  `settings.gradle.kts`; старый `core/fabrication-3d` расформировать.
- Ввести `Fabrication3DResult` / `Fabrication3DError` (по образцу `EngineResult` из
  `engine-api`); внутренние `require` остаются как assertion-ы реализации, но через границу
  API проходят только типизированные коды ошибок с параметрами для локализации.
- Убрать зависимость движка от `core:pipe-calculator`: адаптер `FlangedOffsetAssembly3D`
  переезжает в отдельный мост.
- Прописать движок в `AppGraph`, feature получает интерфейс.
- Расширить `scripts/check_architecture.ps1`: запрет `com.planruler.fabrication3d.engine` в
  `feature/**`, запрет `import android.` в обоих новых модулях.

### Этап 2 — полноценные три измерения (движок)

- **Редактируемый граф:** `updatePart`, `removePart`, `insertBetween`, `setPipeLength`,
  `setElbowAngle`, `setRoll`, `setStartFrame` + пересборка трансформаций ниже по цепочке.
- **Свободное размещение:** стартовый фрейм (позиция + направление + верх) — параметр, а не дефолт.
- **Новые детали:** редукция концентрическая/эксцентрическая, заглушка, тройник как узел
  ветвления маршрута (граф уже это допускает — три порта поддержаны).
- **Решатель v2**, по возрастанию сложности:
  1. аналитика: параллельные торцы (есть), поворот 90° + офсет через 3 отвода, произвольные
     непараллельные торцы через 4 отвода;
  2. численное замыкание (least-squares по длинам труб и кренам) с ограничениями каталога —
     для случаев, где аналитики нет;
  3. целевая ориентация фланца (клокинг болтового рисунка);
  4. минимальные прямые участки между отводами по takeout из каталога;
  5. препятствия как axis-aligned боксы + проверка пересечения маршрута.
- **Геометрические проверки:** самопересечение сборки (капсула–капсула), зазоры между
  параллельными ветками, минимальный радиус гиба.
- Всё — чистые детерминированные функции, без Android, без I/O.

### Этап 3 — параметризация (то, что сейчас не меняется)

`AssemblyProfileOverrides` — слой переопределений над каталогом:

| Параметр | Сейчас | Станет |
|---|---|---|
| Радиус отвода | из каталога | 1D / 1.5D / 3D / произвольный |
| Толщина стенки, зазор под сварку | из каталога / входа | переопределяемые |
| Набор углов отводов | зашит `30/45/60/90` | произвольный набор + пользовательские углы |
| Диапазон угла | `15..90` | `0 < |α| ≤ 180`, ограничение — каталог, а не константа |
| Лимит отводов | константа 5 | настройка в пределах квоты |
| Мин. прямой рез | 10 мм | параметр профиля |
| DN отвода ≠ DN трубы | запрещено | разрешено через редукцию |
| Качество меша | 24/24 | LOD: draft / normal / fine |
| Камера | пресеты, zoom 0.55–4.0, без pan | орбита + pan + zoom, фокус на детали, произвольные углы |

Каждый параметр валидируется с типизированной ошибкой, объясняющей нарушенное правило.
Профиль сохраняется вместе с проектом.

### Этап 4 — UI/ViewModel (минимально; полный дизайн — следующий этап)

- `Assembly3DViewModel`, состояние через `StateFlow`, расчёты в `Dispatchers.Default`.
- Инспектор детали: тап по детали → редактируемые поля → пересчёт сборки.
- Панель параметров движка, ввод стартового фрейма и цели с ориентацией.
- Камера: раздельные жесты орбиты/панорамирования/зума.

### Этап 5 — безопасность и лимиты

- `EngineLimits3D`: максимум деталей, треугольников, глубина undo, число итераций и бюджет
  времени решателя. Превышение → типизированная ошибка, а не OOM/ANR.
- `AssemblyCodec3D`: JSON с версией схемы, строгая валидация на входе, неизвестные поля
  отвергаются, никакой рефлексивной десериализации.
- Движок остаётся без сети и без файлового I/O; всё внешнее — через адаптеры.
- Прогон `scripts/check_architecture.ps1` с новыми правилами и `/security-review` по диффу.

## 5. Предполагаемые тесты

### 5.1 JVM (`core:fabrication3d-api`, `core:fabrication3d-engine`)

- Round-trip кватернионов и трансформаций, ортонормальность фреймов после 10⁴ случайных операций.
- Замыкание маршрута: 14 DN × набор целей, включая непараллельные торцы и повороты на 90°;
  ошибка позиции < 1e-5 мм, ошибка направления < 1e-5°.
- Детерминизм решателя: одинаковый вход → побитово одинаковый выход.
- Редактирование: изменение длины/угла/крена в середине цепочки → `validate()` пуст,
  остальная геометрия пересобрана корректно.
- Удаление и вставка детали, ветвление через тройник.
- Все параметры профиля: граничные и заведомо неверные значения → конкретный код ошибки.
- Квоты: сборка выше лимита деталей/треугольников → `Error(QuotaExceeded)`, не исключение.
- Кодек: round-trip, отказ на мусорном JSON, отказ на неизвестной версии схемы.
- Самопересечение и коллизия с препятствием обнаруживаются.

## 6. Риски

| Риск | Митигация |
|---|---|
| Разделение на два модуля даёт большой diff и задевает все импорты в feature | Золотые тесты этапа 0 фиксируют поведение до рефакторинга |
| Численный решатель для непараллельных торцов — самая сложная часть | Поэтапно: сначала аналитические топологии (3 и 4 отвода), численный метод — только как запасной путь |
| Собственный программный растеризатор ограничивает сложность сцены | Квоты на меш закладываются сейчас; выбор способа рендера — вопрос этапа дизайна |
| Расширение диапазона углов и DN может дать физически нереализуемые сборки | Проверки самопересечения, минимальных прямых участков и takeout из каталога |

## 7. Что в этот этап не входит

Визуальный дизайн, освещение, материалы, анимации, оформление панелей — следующий этап,
после внедрения кодовой базы и прохождения проверок. Здесь только движок, API, параметрика
и тесты.
